## 3. Архитектурные решения

Каждое: решение, обоснование, альтернатива, условие пересмотра.

**D1. Ствол и механика слияния.** Ствол — `origin/main`: на него ссылаются оба внешних плана, его поставка проверена 119 e2e против живого контейнера, версия 0.3.0 опубликована. Сентябрьская работа заезжает одним `git merge` в ветке `rework/merge` (конфликты в 7 доменных файлах решаются по D2/D3), не серией cherry-pick: 31 коммит по 47 общим файлам — это 31 раунд одних и тех же конфликтов. Ветка мержится в `main` только после зелёного гейта A5. Альтернатива (ствол — сентябрьский) отвергнута: перенос поставки и PWA дороже переноса каталога и роутера. Пересмотр: если спайк A2 покажет, что сентябрьская разводка принципиально богаче и дешевле как основа, — меняется местами, механика та же.

**D2. Слоистая модель разводки.** Три слоя с разными скоростями изменения:
- *Электрический граф* (что с чем соединено): основа — октябрьская семантика `Connection{kind: circuit|busbar|bus, terminal, bus}` — на ней валидирован демо-проект и правила `validation.ts`; дополняется типизированными зажимами сентябрьской линии (`TerminalRef`, `TerminalSide`, `TerminalType` из `terminals.ts`).
- *Геометрия по умолчанию* (как рисуется): детерминированный роутер сентябрьской линии `wireRouting.ts` — решения в миллиметрах, assert-ится юнит-тестами без браузера, те же числа кормят SVG и hit-targets.
- *Ручная укладка* (переопределение): изгибы и слои «перед/зад» из ветки coderabbit — необязательный слой поверх: нет переопределения → детерминированный роутер; есть — рисуем точки пользователя, связность не меняется.

Обоснование: три реализации решают три разные задачи и не конкурируют, если развести по слоям. Спайк A2 (3 сценария: запитка от шины, гребёнка, клеммная колодка) проверяет, что слои стыкуются; если нет — откат к октябрьской семантике с переносом роутера позже (что переносим, определяет ADR-запись спайка). Пересмотр: любой сценарий, где слои противоречат друг другу на данных демо-проекта.

**D3. Схема v5.** В `Circuit` добавляется `phaseCount: 1 | 3` (по умолчанию 1); `phase: 1|2|3` остаётся назначенной фазой и имеет смысл только при `phaseCount: 1`. Миграции:
- v1→…→v4 (сентябрьские) и v1→v2 (октябрьские) сохраняются как есть; поверх — v4→v5 и v2→v5.
- Правило неоднозначности: старая цепь с `phase: 3` получает `phaseCount: 1, phase: 3, phaseAmbiguous: true` — это может быть и L3, и трёхфазная; помеченная цепь показывается один раз диалогом при открытии проекта (список: имя цепи, текущее понимание, две кнопки), до уточнения расчёты помечают «фаза не уточнена», инспектор показывает предупреждение. Угадывать по мощности запрещено — оба старых формата двусмысленны одинаково.
- Геометрия разводки: соединения хранятся в терминах графа (D2), ручные изгибы — отдельным необязательным полем.
Пересмотр: если интервью PROD-01 покажет, что пользователям привычнее «тип подключения» из трёх значений (1ф/3ф/нет), расширяем до enum без смены версии.

**D4. Снапшоты.** За основу — номенклатура и платформы октябрьской линии (`board-workspace-…-darwin/linux.png`, 9 файлов). После слияния все png удаляются и переснимаются на darwin и linux; в `verify` остаётся одна визуальная спецификация. Сентябрьская номенклатура (`editor-board`) уходит. Пересъёмка — часть карточки B6, где снимки ещё и рассматриваются глазами.

**D5. Каталог.** Канон — пайплайн сентябрьской линии (`src/data/catalog/` + `tools/generate-enmas.mjs` + `catalog:check`): он уже генерируется и проверяется. `src/data/catalog/index.ts` экспортирует API, совместимый с 6 местами октябрьской линии. `verification.ts` (сентябрьская) и `provenance.ts` (октябрьская) сливаются в один модуль статуса позиции: источник, версия, отдельные статусы характеристик и геометрии. `city9` остаётся удалённым (решение от 29.09 — рисуем только по чертежам пользователя), включая октябрьский `public/models/city9-mcb-2p.glb`.

**D6. ИИ-прокси.** Прокси становится опциональным сервисом в `docker-compose.yml` (profile `ai`): подняли с профилем — работает, не подняли — приложение честно сообщает «ИИ недоступен». CSP-шаблон nginx параметризуется адресом прокси при сборке контейнера (env → `envsubst` → конфиг), значение по умолчанию выключено. Dev-сценарий (`npm run ai` + `VITE_AI_PROXY_PORT`) документируется как основной локальный. Запрещённое состояние: CSP, указывающая на loopback посетителя.

**D7. PWA-обновление.** В регистратор service worker добавляется обработка `updatefound` → ненавязчивый промпт «доступна новая версия — применить»; по согласию `postMessage(SKIP_WAITING)` и перезагрузка по `controllerchange`; активные вкладки старой версии получают то же уведомление. Тест — `service-worker.test.ts` расширяется на новую логику, сценарий вручную на собранном контейнере.

**D8. Тесты.** Оба юнит-набора сохраняются (~474 + ~244, коллизии имён файлов решаются переименованием по принадлежности); оба e2e-набора — октябрьская конфигурация (`test:e2e`, `test:preview`, `playwright.deploy.config.ts`) + сентябрьские спецификации. `verify` ствола: `typecheck && test && catalog:check && test:e2e && test:preview`. Коллизии спецификаций с одинаковыми именами (`editor-2d`, `settings`, …) решаются сравнением: остаётся версия, проверяющая живое поведение объединённого ствола, а не сентябрьский экран.

## 4. Фаза A — консолидация

Порядок A0 → A1 → A2 → (A3, A4 параллельно) → A5 → A6. Оценки — ориентировочные, в рабочих днях одного разработчика.

### A0. Зафиксировать сентябрьскую линию
- **Пользователь и проблема:** работа на 31 коммит и 84 файла существует в одном экземпляре на одной машине; риск потери — недели работы.
- **Что входит:** сверка с параллельной сессией (риск R1) — какие из 84 файлов её; свои файлы коммитятся логическими порциями (каталог, CHINT-модели, разводка v3, планировщик v4, e2e); пуш ветки `september-line`; тег `september-final`.
- **Зависимости:** нет. **Формат:** без изменений схемы.
- **Критерии приёмки:** `git status` пуст; ветка на origin; `npm test` на ветке зелёный.
- **Откат:** не требуется (только добавление). Чужие файлы не коммитятся до подтверждения их сессии.

### A1. Ветка слияния и заготовка золота
- **Проблема:** слияние нельзя делать вслепую; нужна проверяемная база «старое открывается».
- **Что входит:** `rework/merge` из `origin/main`; золотой набор проектов: демо-проект обеих линий + фикстуры схем v1–v4 из `project-schema`-тестов + 2–3 ручных проекта с CAD-архивами; скрипт `tools/golden-check.mjs` — открыть/мигрировать/пересохранить каждый, сверить контрольные суммы смысловых полей; тег `pre-rework` на `main`.
- **Зависимости:** A0. **Формат:** без изменений.
- **Критерии:** золотой набор проходит на обоих родителях до слияния (фиксация исходной точки).
- **Откат:** тег `pre-rework`.

### A2. Спайк слоистой разводки
- **Проблема:** D2 — предварительное решение; нужно подтвердить на коде, а не на бумаге.
- **Что входит:** на ветке `rework/merge` поднять три сценария (запитка от шины N/PE, гребёнка, клеммная колодка) на данных демо-проекта октябрьской линии; проверить: октябрьские соединения + сентябрьские `TerminalRef` совместимы; роутер `wireRouting.ts` принимает граф без переделки семантики; переопределение изгибов coderabbit ложится поверх без изменения связности. Выход — короткий ADR в этом файле (приложение 1): подтверждение или построчный план Б.
- **Зависимости:** A1. **Формат:** без изменений (спайк не мигрирует).
- **Критерии:** три сценария рисуются и валидируются; ADR записан; решение D2 подтверждено или заменено.
- **Проверки:** юнит-тесты трёх сценариев остаются в стволе как регрессионные.
- **Откат:** ветка спайка удаляется, план Б становится содержимым A3/A4.
- **Оценка:** 2–3 дня.

### A3. Каталог на ствол (D5)
- **Пользователь и проблема:** ствол (октябрьский) не знает JSON-каталога, генерации и 15 моделей CHINT; сентябрьский каталог не знает октябрьских потребителей API.

- **Зависимости:** A2 (порядок файлов). **Формат:** снимок каталога в ревизии проекта — откладывается до C3, здесь только API.
- **Критерии:** все 6 октябрьских мест импорта работают; `catalog:check` зелёный; спецификация BOM согласована с новыми статусами.
- **Проверки:** юнит-тесты каталога обеих линий; e2e `catalog-verification.spec.ts`.
- **Откат:** каталог заезжает отдельным коммитом — `git revert` одного коммита.

### A4. Слияние домена и схема v5 (D2, D3)
- **Пользователь и проблема:** проект, сохранённый любой из старых линий, должен открываться в объединённом стволе без молчаливой подмены смысла.
- **Что входит:** разрешение конфликтов в 7 доменных файлах по D2/D3; миграции v2→v5 и v4→v5; флаг `phaseAmbiguous` и диалог уточнения; `Connection` в терминах графа + необязательные изгибы; перенос `LinesPanel.vue` и планировщика; `voltageDrop.ts`, `terminals.ts`.

- **Критерии:** золотой набор A1 проходит `golden-check` (открыть/мигрировать/пересохранить) на всех версиях v1–v4; неоднозначные `phase: 3` показываются диалогом, а не угадываются; демо-проект октябрьской линии валидируется без новых ошибок.
- **Проверки:** расширенные `project-schema.test.ts` (таблица миграций), `validation.test.ts`, новые тесты трёх сценариев A2.
- **Откат:** слияние — один merge-коммит; откат = `git reset --hard pre-rework` до пуша в `main`. После пуша — forward-fix, откат миграции данных не предусмотрен (поэтому гейт A5 перед пушем).

## 5. Фаза B — надёжная основа

Можно начинать B1–B3 сразу после A4 (до merge в `main`, на ветке `rework/merge`).

### B1. Разделить фазу и количество фаз (ENG-01)
- **Пользователь и проблема:** сборщик выбирает «L3» для однофазной линии, а расчёт считает её трёхфазной (или наоборот); ошибка невидима до печати.
- **Сценарий:** пользователь назначает линии L1; выбирает «трёхфазная» отдельным полем; расчёт, подписи на схеме и маркировка показывают выбранное без сюрпризов.
- **Что входит:** `phaseCount` в домене уже из A4; здесь — UI-завершение: инспектор использует существующее разделение (`InspectorPanel.vue:21-27`), однолинейная схема и печать различают 1ф/3ф; диалог уточнения из A4 полируется; `phaseAmbiguous` сбрасывается только явным выбором.
- **Зависимости:** A4. **Формат:** уже v5.
- **Критерии:** в UI нет поля, где выбор «3» меняет сразу два смысла; старый проект с неоднозначностью открывается с диалогом и без него не считается проверенным.
- **Проверки:** юнит: `phaseCount=3` распределяется по трём корзинам, `phase=3,phaseCount=1` — только в L3; e2e: назначение фазы и смена количества фаз.
- **Откат:** обычный revert; данные v5 обратно совместимы (поля читаются обеими трактовками через флаг).

### B2. Расчёты тока/мощности/баланса (ENG-02)
- **Проблема:** `electrical.ts:47` кладёт трёхфазную цепь в корзину L3; формула переключается по `phase === 3` (`electrical.ts:69-74`).
- **Что входит:** расчёт по `phaseCount` + `phase`; однофазная 4600 Вт = 20 А при 230 В на любой фазе; трёхфазная — по трём корзинам; свёртка итогов, однолинейная схема и ИИ-контекст используют одни функции.
- **Критерии:** числовой пример из плана развития проходит на L1, L2 и L3; трёхфазный пример — отдельно.
- **Проверки:** табличные юнит-тесты с независимым пересчётом вручную; e2e на демо-проекте сверяет подписи.
- **Откат:** revert; формат не меняется.

### B3. ИИ-сводка из диагностики (AI-01)
- **Проблема:** `assistantContext.ts:144,178` считает цепь с битой ссылкой защищённой; логика дублирует `validation.ts:141-143` и расходится с ним.
- **Что входит:** счётчики сводки выводятся из `issues` (один источник истины); тест на три случая: пустая ссылка, битая ссылка, ссылка на аппарат без определения.
- **Критерии:** сводка не сообщает число, которое противоречит диагностике, ни на одном проекте золотого набора.
- **Проверки:** юнит-пары «проект → issues → сводка» на золотом наборе A1.
- **Откат:** revert.
