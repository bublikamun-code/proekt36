# Runbook локального preproduction «Панель 36»

## 1. Границы версии

Версия пригодна для локальной демонстрации, UX-проверки и предварительной подготовки 2D-компоновки. Она не содержит серверной учётной записи, синхронизации между устройствами, серверных прав доступа, оплаты, checkout, webhooks и публичного API.

Основной режим редактора — 2D. Полноценный 3D-редактор и 3D Viewer не являются частью релиза. Город9 остаётся отдельным тестовым образцом и не объединяется с официальными позициями ENMAS/CHINT. NB1-63DC исключён.

## 2. Запуск

```bash
npm install
npm run dev
```

Production-сборка и локальный просмотр:

```bash
npm run build
npm run preview
```

`vite preview` проверяет собранные статические файлы, но не заменяет настройку будущего CDN или web-сервера.

## 3. Проверки

```bash
npm run verify
```

Для диагностики запускайте этапы отдельно. Playwright использует Chromium; перед первым запуском при необходимости установите браузер командой `npx playwright install chromium`.

Проверки охватывают:

- TypeScript и Vue templates;
- schema v1 → v2, недействительные импорты и ссылки;
- footprint, транзакционные команды и миграцию корпуса;
- localStorage/IndexedDB, quota/security errors и per-project undo/redo;
- неизвестные цены и безопасный CSV;
- DEMO без локальных побочных эффектов;
- маршруты, диалоги, клавиатуру, печать и production deep links.

## 4. Хранение и восстановление

### Основные хранилища

| Данные | Хранилище | Примечание |
|---|---|---|
| Проекты и текущий проект | `localStorage` | Только в текущем браузере и origin |
| Последний валидный снимок | `localStorage` | Используется при повреждении основного снимка |
| Повреждённый исходный JSON | `localStorage` recovery key | Не удаляется молча при следующей записи |
| Журнал пакетной записи | `localStorage` `panel36.storage.journal.v1` | Живёт только во время записи; при аварийном закрытии вкладки восстанавливается при следующем запуске |
| GLB/glTF/ZIP | `IndexedDB` | Бинарные данные остаются на устройстве |
| DEMO | Не использует пользовательские хранилища | Только детерминированный fixture |

При `QuotaExceededError`, `SecurityError` или блокировке хранилища интерфейс показывает actionable-состояние. Данные, которые не удалось записать, следует экспортировать вручную.

Один снимок щита разложен по трём ключам, а транзакции между ключами у `localStorage` нет. Поэтому перед пакетной записью прежние байты сохраняются в `panel36.storage.journal.v1`: отказ на любом ключе откатывает всю пачку сразу, а если вкладку закрыли или убили посередине, журнал восстанавливается при следующем запуске. Не пустой журнал после старта — повод выгрузить проекты вручную и проверить свободное место.

### Экспорт проекта

Кнопка «Экспорт» создаёт `.panel36.json`. Конверт включает:

- `application` и `applicationRevision`;
- `schemaRevision`;
- `catalogRevision` и snapshot каталога;
- `validationRevision`;
- полный объект `project`;
- `cadModelManifest` и `cad.binaryIncluded: false`.

Импортируются raw-проекты v1/v2 и поддерживаемые конверты. Будущие версии схемы и неизвестные ревизии отклоняются с сообщением пользователю.

### Резервная копия

Кнопки «Создать копию» и «Восстановить» работают с `panel36.backup.v1`. Восстановление заменяет текущий список проектов и сбрасывает их историю, поэтому перед подтверждением показывается отдельный диалог. Локальная библиотека CAD-моделей не удаляется.

Если проекты в копии ссылаются на импортированные модели, которых нет в catalog snapshot, копия
сообщает об этом до подтверждения, а после восстановления такие аппараты помечаются как «нет в
каталоге» и ждут повторного импорта. Отказ от восстановления здесь был бы хуже: он делает копию
непригодной целиком после очистки браузера.

### Архив с CAD-моделями

JSON-экспорт и копия `panel36.backup.v1` геометрию не содержат: в конверте стоит
`cad.binaryIncluded: false`, потому что в JSON нет места для GLB. Поэтому проект, который
использует импортированную модель, нужно сохранять **архивом**.

Кнопки «Экспорт с моделями» (редактор и карточка проекта) и «Копия с моделями» (список проектов)
собирают `.panel36.zip`:

| Запись | Что это |
|---|---|
| `project.panel36.json` | тот же конверт, что и у обычного JSON-экспорта |
| `backup.panel36.json` | та же копия `panel36.backup.v1` |
| `cad/manifest.json` | полные метаданные каждой модели плюс размер |
| `cad/models/<id>.bin` | геометрия |
| `README.txt` | что это и как вернуть |

Сборка, которая не знает про архив, прочитает `project.panel36.json` оттуда — конверт внутри
архива побайтно тот же. Импорт принимает и `.json`, и `.zip` в одном поле выбора: различаются они
по сигнатуре файла, а не по кнопке.

Ограничения: до 200 МБ на архив, до 100 МБ распакованных данных, до 256 записей, до 50 МБ на
модель. Путь модели строится по идентификатору, а не по имени файла, поэтому имя с `/` не может
вывести файл за пределы `cad/models/`.

При восстановлении байты каждой модели проходят `validateModelFile` — ту же проверку, что и
ручной импорт. Архив не является обходом правил импорта: повреждённая модель будет отклонена, а
модель, чей идентификатор уже есть в библиотеке, не перезаписывается. Модель, которая не
вернулась, видна как «нет в каталоге» — и это честнее, чем молча подставлять пустую геометрию.

## 5. Ограничения CAD

- GLB: до 50 МБ, glTF 2.x.
- Автономный JSON glTF: до 50 МБ, внешние `buffer`/`image` запрещены.
- ZIP: до 50 МБ сжатого и до 100 МБ распакованного содержимого, не более 256 записей.
- Запрещены абсолютные и выходящие за пределы архива пути.
- Файлы проверяются и сохраняются только в IndexedDB браузера.
- Пользовательские данные не отправляются на сервер или во внешние сервисы.

Валидация файла не заменяет проверку геометрии, материалов, единиц, авторских прав и производственной пригодности модели.

## 6. Расчёты и печать

Приложение выполняет предварительную компоновку и поддерживаемые диагностические правила. Проверяются, в частности, переполнение рядов, пересечения, отсутствующие товары, ссылки цепей/подключений, дубли, базовая согласованность L/N/PE и фаз.

`VALIDATION_REVISION` равна 3. Правила, добавленные в этом наборе:

| Код | Уровень | Что означает |
|---|---|---|
| `electrical.phase-imbalance.preliminary` | warning | разброс нагрузки по фазам выше 30 %; считается, только если нагружены хотя бы две фазы |
| `circuit.shared-protection.overload` | warning | сумма цепей, защищаемых одним аппаратом, выше его номинала |
| `circuit.conductor.cross-section` | warning | сечение провода не держит номинал защиты (In ≤ Iz) |
| `circuit.power.current.mismatch` | warning | мощность подразумевает ток больше, чем объявлено у цепи |
| `circuit.power.over-protection` | warning | мощность подразумевает ток больше номинала защиты |
| `circuit.current.undetermined` | info | задана мощность, ток — нет; ток не попадёт в расчёт фаз |
| `device.address.missing` | warning | аппарат без обозначения |
| `device.address.duplicate` | error | два аппарата с одинаковым обозначением |

Справочник сечений — `src/domain/conductorSpec.ts`: допустимый ток медной жилы с ПВХ-изоляцией
при групповой прокладке (метод B1, 30 °C, в коробе). Для сечения, которого нет в списке
инспектора и которое могло прийти из импорта, ёмкость интерполируется между соседними строками.
Номинал выше 580 А справочник не оценивает, и проверка молчит, а не выдумывает значение.

Про согласованность мощности и тока: цепь проектируют с запасом, поэтому нагрузка меньше
объявленного тока — норма и не remark. Сообщается только то, что не может быть верным, и
ни одно из двух чисел не переписывается молча.

Не выполняются полноценные расчёты селективности, термического режима, КЗ/УЗ, нагрузочной
способности, компенсации реактивной мощности, заземления, падения напряжения и нормативного
проектирования.

Печатный отчёт содержит однолинейную схему, компоновку, позиции, соединения как диагностические
связи, BOM, проверки, ревизии и disclaimer. Однолинейная схема строится из цепей и их защитных
аппаратов в `src/domain/singleLine.ts` и показывает путь питания. Она не является принципиальной
схемой или монтажной документацией: аппарат без цепей перечисляется под схемой, а цепь с
потерянной защитой рисуется отдельной колонкой «нет защиты», а не приписывается соседнему
автомату.

Цена `0` и неизвестная цена — разные состояния. Если цена не подтверждена, интерфейс показывает «уточняется» и не объявляет коммерческую сумму.

## 7. ИИ-помощник по сборке щита

Помощник отвечает по **сводке** щита и может предложить ограниченный набор изменений настроек. Ключ провайдера в браузере не хранится: запросы идут на локальный прокси, и уже он обращается к провайдеру.

Запуск в отдельном терминале:

```bash
cp tools/ai-proxy.env.example tools/ai-proxy.env   # заполнить AI_API_KEY
npm run ai
```

Прокси слушает только `127.0.0.1:8787`, принимает только origins вида `http://127.0.0.1:*` или `http://localhost:*`, ограничивает тело запроса 256 КБ и не пишет содержимое запросов в журнал. Поддерживаются провайдеры `anthropic` и `openai`; выбор делается переменными `AI_PROVIDER`, `AI_API_KEY`, `AI_MODEL`, необязательными `AI_BASE_URL` и `VITE_AI_PROXY_PORT`.

Порт прокси задаётся одной переменной `VITE_AI_PROXY_PORT`, которую читают все трое участника: сам прокси, браузерный клиент и `connect-src` в CSP сборки. Поэтому менять порт нужно только в ней и пересобирать приложение — значение запекается на этапе сборки. Переменная с префиксом `VITE_` выбрана потому, что именно такие переменные сборка отдаёт браузеру; добавлять `AI_` в `envPrefix` нельзя, иначе вместе с портом в клиентский бандл попал бы и `AI_API_KEY`.

Панель помощника находится внизу инспектора. Если прокси не запущен или в нём не задан ключ, панель показывает это состояние и команду запуска, а не ошибку. Приложение остаётся полностью рабочим без прокси: помощник — необязательный слой.

**Что уходит провайдеру.** Ровно то, что перечислено в блоке «Что уходит провайдеру» внутри панели: ревизии приложения и каталога, пресет, сеть и геометрия корпуса, число занятых и свободных модулей, разбивка по категориям и рядам, счётчики цепей и распределение токов по фазам, а также коды и заголовки сработавших проверок без их текстов.

**Что не уходит никогда.** Название и идентификатор проекта, адреса, маркировки, примечания, `instanceId` и `productId`, названия и артикулы аппаратов, названия цепей и нагрузок, подписи подключений, бинарные CAD-модели и тексты проверок. Сборка сводки находится в одном месте — `src/domain/assistantContext.ts`, а `tests/assistant-context.test.ts` и `tests/e2e/assistant.spec.ts` проверяют, что запрещённых значений в payload нет.

Предложения помощника не применяются молча: подписи кнопок собирает приложение, не модель; переход на другой корпус или рейку идёт через существующий диалог миграции; изменение настроек — обычная операция с отменой по Ctrl+Z. Перечень допустимых действий ограничен шестью: `cabinet.migrate`, `rail.migrate`, `settings.reserve`, `settings.inputCurrent`, `catalog.focus`, `rows.compact`. Всё остальное, включая неизвестные коды и выход значений за диапазон, отбрасывается с объяснением. Так как модель видит только сводку, предложения формулируются формой («корпус на 48 модулей в 4 ряда»), а конкретную позицию каталога выбирает приложение.

## 8. Будущий хостинг

При развёртывании статической сборки любой неизвестный путь приложения должен возвращать `index.html` (SPA fallback). Например, прямой запрос `/app/projects/<id>/editor` не должен возвращать HTTP 404. Ошибка должна возвращаться только для отсутствующих файлов вроде `/assets/missing.js`.

Примеры будущих правил:

- Nginx: `try_files $uri $uri/ /index.html;`
- Netlify: SPA redirect для всех маршрутов на `/index.html`;
- Vercel: filesystem-first rewrite всех прочих путей на `/index.html`.

До появления серверного слоя не добавляйте API routes, auth redirects или cookie-сессии, если они не покрыты отдельным threat model и тестами.

## 10. Версия и выпуск

Версия приложения записана в коде в одном месте — `src/version.ts`. Из неё берутся `APPLICATION_REVISION`, поля `application.revision` и `applicationRevision` в конверте экспорта и подпись в подвале публичных страниц. Второе место, `version` в `package.json`, существует потому, что его требует npm; обычный модуль выбран вместо подстановки на этапе сборки, потому что версию читают Vite, Vitest и Playwright, и каждому конфигу пришлось бы описывать подстановку заново.

Рядом с версией приложения живут ревизии содержимого, каждая из которых сравнивается по своей шкале:

| Ревизия | Где | Что означает |
|---|---|---|
| `APP_VERSION` | `src/version.ts` | версия приложения, semver |
| `version` в `package.json` | корень | то же значение для npm |
| `PROJECT_SCHEMA_VERSION` | `src/domain/projectSchema.ts` | версия схемы проекта, целое |
| `CATALOG_REVISION` | `src/data/catalog.ts` | ревизия каталога, дата и номер |
| `VALIDATION_REVISION` | `src/domain/projectSchema.ts` | набор правил проверок, целое |

Файл, созданный более новой версией приложения, отклоняется при импорте — сравнение ревизий описано в разделе 4. При изменении схемы, каталога или правил проверок поднимайте минорную версию, иначе пользователь получит проект, который его сборка прочитать не сможет.

Порядок выпуска:

1. `npm run verify` завершён без ошибок.
2. `npm version <patch|minor>` обновляет `package.json`; затем то же значение ставится в `src/version.ts`.
3. Добавлен раздел в `CHANGELOG.md` с датой и списком изменений.
4. Коммит и тег: `git commit -am "release: <версия>"` и `git tag -a v<версия> -m "<версия>"`.

`tests/app-version.test.ts` падает, если версия в коде разойдётся с `package.json`, поэтому расхождение нельзя пропустить незаметно: тест входит в `npm test`, а значит и в `npm run verify`.

Репозиторий ведётся в git, удалённый репозиторий — `origin`. Ключ провайдера ИИ-помощника в коммиты не попадает: `tools/ai-proxy.env` исключён в `.gitignore`, а `tools/ai-proxy.env.example` содержит только placeholder.


## 11. Модель угроз локального прокси

Прокси `npm run ai` держит API-ключ и слушает только `127.0.0.1`. Что из этого следует.

**Кто может до него достучаться.** Любой процесс, запущенный на этой машине, отправляет
`POST http://127.0.0.1:8787/chat` и тратит ключ. Аутентификации и лимита частоты нет — это
осознанно: инструмент одноразовый и живёт только на loopback. Если прокси держится открытым
дольше рабочего дня, ключ стоит считать скомпрометированным и перевыпустить у провайдера.

**Кто не может.** Сайт в браузере с чужого домена: `Origin` проверяется, чужой источник
получает 403 и на preflight, и на самом запросе. DNS-rebinding тоже не проходит — адрес
подставляется в проверку как есть, а не по фактическому соединению.

**Куда уходит ключ.** На адрес из `AI_BASE_URL`, а при пустом значении — на официальный адрес
выбранного провайдера. Если `AI_BASE_URL` задан, прокси печатает предупреждение при старте: это
единственный способ случайно отправить ключ не туда, поэтому он громкий. Для локальной модели
ожидаемое значение — `http://127.0.0.1:<порт>/v1`.

**Что уходит из браузера.** Только сводка из `src/domain/assistantContext.ts`: количества,
суммы, доли по категориям и заголовки замечаний. Названий, адресов, маркировок, примечаний и
моделей в ней нет вообще, поэтому подсказка из данных проекта не может дойти до модели даже
случайно. Проверяется в `tests/e2e/assistant.spec.ts` по фактическому телу запроса.

**Что может сделать ответ модели.** Ничего напрямую. `buildAction` в `src/services/aiAssistant.ts`
принимает закрытый список из шести кодов, каждый параметр пере-resolve-ится по собственному
каталогу приложения, числа проверяются по диапазонам, текст обрезается до 240 символов. Любое
предложение показывается пользователю с названием и причиной до применения.

**Чего прокси не делает.** Не хранит запросы, не логирует тела, не пересылает ничего, кроме
одного запроса к провайдеру.

## 12. Content-Security-Policy

Политика собирается плагином в `vite.config.ts` и попадает в `dist/index.html` как `<meta>` при
сборке. В разработке она выключена намеренно: тот же тег сломал бы HMR Vite.

Что уже обеспечено: `script-src 'self'` без исключений, `object-src 'none'`, `base-uri 'self'`.
Инлайновые `style`-атрибуты разрешены через `style-src-attr` — без них не позиционируется 2D-щит;
старый `style-src` оставлен с тем же допуском как запасной вариант для браузеров, которые не знают
`style-src-attr`.

Проверка: `tests/preview-smoke.spec.ts` требует, чтобы политика была в собранной странице и
содержала `script-src 'self'`, `object-src 'none'` и `http://127.0.0.1:8787`.

Чего в `<meta>` сделать нельзя: `frame-ancestors` и `form-action` браузер в мета-теге
игнорирует. Если проект будет раздаваться с настоящего сервера, их нужно отдавать заголовками
ответа — вместе с ними полезно добавить `Strict-Transport-Security`.

## 13. Офлайн-оболочка

Приложение целиком работает на устройстве, поэтому в production-сборке оно ставится как
приложение (манифест `public/manifest.webmanifest`, иконки, service worker `public/sw.js`) и
открывается без сети.

Правила `sw.js`:

- навигация — всегда сначала сеть, и только при отказе берётся `/index.html` из кэша. Все
  маршруты SPA отдаются одним и тем же документом, и ответ из кэша скрывал бы новую сборку
  бесконечно;
- `/assets/*` и `/models/*` — cache-first: имена файлов сборки хешированы и не меняются;
- кэшируются только ответы `ok` и `basic`, чтобы в кэш не попал частичный или непрозрачный ответ;
- имя кэша содержит версию приложения, и `activate` удаляет все `panel36-*`, кроме текущих, —
  поэтому новый документ никогда не получит чанк предыдущей сборки.

Регистрация (`src/services/serviceWorker.ts`) пропускается, если: сборка не production, контекст
небезопасен, `serviceWorker` не поддерживается, вкладка уже управляется worker'ом или браузером
управляет автотест (`navigator.webdriver`). Последнее условие обязательно: у Playwright настоящий
кэш, и кэш оболочки из одного прогона читался бы как документ следующего.

В CSP добавлено `worker-src 'self'`. Без этой директивы регистрация в production-сборке
блокируется, и это выглядит как «просто не работает офлайн» — ошибки в консоли нет.

`public/sw.js` — статический файл, он не может импортировать `src/version.ts`, поэтому версия
кэша записана в нём строкой. Расхождение с версией приложения ловит
`tests/service-worker.test.ts`. **При выпуске версию в `sw.js` нужно поднять вместе с
`src/version.ts` и `package.json`.**

## 14. Происхождение позиций каталога

Каждая позиция каталога имеет обязательный `verificationStatus`, и формулировка статуса одна на
все интерфейсы (`src/domain/provenance.ts`):

| Статус | Метка | Источник |
|---|---|---|
| `verified` | Подтверждено | параметры сверены, `sourceUrl` обязателен |
| `unverified` | Параметры не подтверждены | реальное изделие без сверки с паспортом; `sourceUrl` **нет** |
| `template` | Шаблон | строка сгенерирована по серии; `sourceUrl` серии допустим |
| `legacy` | Исторические данные | данные прошлой редакции |

Правило, которое стоит сохранять: `sourceUrl` не ставится позиции, параметры которой никто не
проверял. Правдоподобный URL изделия, которое не открывали, — это заявление, которого каталог
не может поддержать, и он делает список читающимся лучше, чем он есть.

Сейчас 39 встроенных позиций имеют статус `unverified`: изделия настоящие (EKF, IEK, ABB,
Schneider, DEKraft, DKC), параметры взяты из первого среза проекта и не сверялись. Если позиция
получила проверку по паспорту — переведите её в `verified` и добавьте `sourceUrl`; это единственный
способ, которым статус `verified` вообще появляется.

## 15. Новая рабочая область

Две рабочие области живут одновременно и это не ошибка.

- `/app/editor` — старая, проверенная. Редактор рисует каждый аппарат отдельным вложенным `<svg>`,
  масштабированным под пиксельную ширину, тогда как доска работает в миллиметрах корпуса. Две
  системы координат на одном экране: провод мог попасть в нужный столбец и промахнуться по
  вертикали на 21 пиксель. Чинить это значит подгонять каждую следующую механику.
- `/app/board` — новая. Сцена собирается в `src/domain/boardScene.ts` целиком в миллиметрах и
  рисуется одним SVG; пересчёт в пиксели происходит один раз, на `viewBox`.

**Проверка, ради которой всё затевалось.** `tests/e2e/board-scene.spec.ts` измеряет конец каждого
провода в экранных пикселях через `getScreenCTM` и сравнивает с центром зажима, в который он
приходит. Сейчас расстояние равно нулю для всех проводов. Если это перестанет быть правдой, тест
падает — и это единственная проверка, которая ловит расхождение двух систем координат.

**Что уже есть в новой области:** доска и зажимы, провода с трассировкой в зажимы, каскадные
соединения, выбор аппарата кликом, масштаб под ширину окна, каталог и инспектор (те же компоненты,
что и в старом редакторе), размещение по клику, отмена и повтор, печатный отчёт с листом
маркировки, визуальный эталон.

**Перетаскивание работает:** из каталога на доску и перенос установленного аппарата вместе с
соседями.

**Что ещё не перенесено:** меню проектов, сохранение и экспорт (включая экспорт с CAD-моделями),
импорт файла проекта, переключение темы, восстановление из резервной копии, импорт CAD-моделей.

## Паритет: одна линейка на обе доски

`tests/e2e/wire-landing.spec.ts` открывает **один и тот же проект с проводами** на обеих досках и
меряет одно и то же: конец каждого пути против центра ближайшего зажима. Обе точки читаются через
`getScreenCTM`, поэтому результат в пикселях экрана и не зависит от того, как вид выбрал себя
масштабировать.

| Доска | проводов | в зажимах | худшее расстояние |
|---|---|---|---|
| `/app/editor` (старая) | 10 | 0 | 20.3 px |
| `/app/board` (новая) | 10 | 10 | 0.3 px |

Число зажимов у обеих ��а��ок — 104, то есть сравнение идёт на равных. Разница в 20 пикселей это
не погрешность отрисовки, а вторая система координат: у старой доски корпус аппарата рисуется вложенным
SVG в собственном масштабе, тогда как плита масштабируется иначе. Новая доска рисует лицо аппарата
в тех же миллиметрах, что и плиту, и преобразование у неё ровно одно.

Гейтом в тесте служит новая доска. Старая только измеряется: она заменяемая, и красный тест на ней
сказал бы не о готовности новой, а повторил бы тот самый результат, который и породил переработку.

Визуальные эталоны есть у обеих досок: `editor-board` для старой и `board-workspace` для новой.

**Почему маршрут по умолчанию всё ещё старый.** `/app` открывает `/app/editor`. Переключать его
на новую область имеет смысл только вместе с переносом перечисленного выше: пользователь, пришедший
из списка проектов, должен по-прежнему сохранять проект, экспортировать архив с моделями и
переключать тему. Трассировка уже подтверждена, но обвязка ещё не догнала.

Демо-проект для проверки трассировки открывается на `/app/board?fixture=demo`.

**Когда переключать маршрут по умолчанию:** когда новая область пройдёт те же браузерные тесты и
визуальные эталоны, что и старая. До этого момента обе доступны, и выбор за пользователем.
