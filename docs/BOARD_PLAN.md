# План рабочей панели щита

Документ этапа 0. Здесь факты: что доска умеет, чего не умеет, и какие решения она не может
принять сама. Ничего из дальнейших этапов здесь не проектируется — это отдельная работа после
того, как основа будет согласована.

## 1. Что уже есть в домене и в сторе — и почти не используется доской

Это главный вывод инвентаризации. Большая часть нужной логики **уже написана**, и доска до неё
просто не дотягивается. Отсюда и ощущение «симпатичная оболочка, бесполезная панель».

Стор уже умеет, среди прочего:

| Действие | Метод | Видно ли на доске сегодня |
|---|---|---|
| Поставить аппарат | `addDevice` | да, кликом из каталога |
| Сдвинуть аппарат | `moveDeviceById`, `moveSelected` | да, перетаскиванием |
| Сдвинуть на модуль | `nudgeSelectedDevice` | нет |
| Удалить выбранное | `deleteSelected` | нет |
| Дублировать выбранное | `duplicateSelected` | нет |
| Изменить параметры | `updateSelected` | только через панель |
| Уплотнить ряд | `compactSelectedRow`, `compactAllRows` | нет |
| Перенумеровать адреса | `autoNumberAll` | нет |
| Создать цепь | `addCircuit` | только через панель |
| Создать/изменить/удалить подключение | `addConnection`, `updateConnection`, `deleteConnection` | только через панель |
| Отмена и повтор | `undo`, `redo` | отмена есть |
| Экспорт и импорт | `downloadProject`, `importProject` | нет |

Проверок в домене 20+, среди них `circuit.connection.missing`, `device.address.missing`,
`device.address.duplicate`, `connection.bus.unknown`, `electrical.current.preliminary`.

**Вывод по этапам 1, 2, 4, 5, 6:** это в основном слой взаимодействия, а не новая логика. Слой
взаимодействия как раз и отсутствует.

## 2. Главное ограничение модели: зажима в ней нет

`Connection` описывается так:

```
{ circuitId, fromBus, toDeviceId, fromDeviceId?, kind, color, thickness, label }
```

То есть связь — это **«шина → устройство»**, а не **«зажим → зажим»**. Конкретный зажим в проекте
нигде не записан: он вычисляется при отрисовке (`src/domain/wiring.ts` решает, какая колонка
зажима соответствует какой шине, по позиции устройства).

Из этого следует, что формулировка этапа 3 в исходном плане — «клик по зажиму, клик по второму
зажиму» — **на текущей модели невыполнима**: негде записать, какой именно зажим выбрали.

### Два варианта, и это решение не моё

**А. Провод несёт шину, зажим выводится.**
Клик по зажиму определяет шину (L, N или PE — она уже известна по колонке), второй клик — второе
устройство. В проекте пишется `{ fromBus: 'L', fromDeviceId: A, toDeviceId: B }`. Модель не меняется,
совпадает с уже существующим каскадом QF01→QF02. Стоимость: почти нулевая.

**Б. В модели появляется явный зажим.**
`{ fromTerminal: { deviceId, index } }`. Тогда можно соединить, например, левый зажим одного
аппарата с правым зажимом другого. Цена: миграция схемы, правка валидации, отчёта, однолинейной
схемы, печати. Зато провод выглядит на доске ровно так, как его вывели.

Разница видна человеку: в варианте А нельзя взять две разные шины в один «клик», в варианте Б
можно соединить конкретные клеммы, а не абстрактные шины.

## 3. Чего доска не умеет по существу

1. **Режимов нет.** Любой клик означает «выделить». Провод, удаление, правку адреса руками не
   провести.
2. **Провод нельзя провести на доске.** Подключения создаются только формами в панели.
3. **Аппарат нельзя удалить или продублировать**, хотя стор это умеет.
4. **Адрес нельзя поправить на корпусе.**
5. **Проверки не нарисованы.** Двадцать правил живут списком в панели; свободный зажим на доске
   не виден.
6. **Нет сохранения, экспорта, импорта и CAD.** Для рабочей панели это блокер.

## Ход работы

### Этап 0 — инвентаризация. Сделан.

Документ выше. Отдельно зафиксировано: этапы 1, 2, 4, 5, 6 — слой взаимодействия, а не новая
логика, потому что стор уже умеет всё из таблицы раздела 1.

### Этап 1 — инструменты доски. Сделан.

Критерий, проверенный в браузере (`tests/e2e/board-tools.spec.ts`):

1. `2` включает режим адреса, кнопка нажата, второй инструмент отжат.
2. Клик по аппарату открывает поле с его адресом; Enter записывает и возвращает «Выбрать».
3. Esc отменяет правку, адрес на доске не изменился.
4. Клик мимо в режиме адреса не меняет проект.
5. В режиме адреса аппарат не перетаскивается.

Инструмент «Провести» в панели **нет**: он появляется на этапе 3 вместе с реальным проведением
провода. Кнопка, обещающая провод, который нельзя провести, вводила бы в заблуждение.

### Этап 2 — жизненный цикл аппарата. Сделан.

Критерий: Delete убирает аппарат вместе с его проводами, одна отмена возвращает и то и другое;
Ctrl+D ставит копию и выделяет её.

Попутно исправлено в сторе: `duplicateSelected` отказывался, если ряд оригинала заполнен, и просто
ничего не делал. Теперь копия сначала ищется рядом с оригиналом, а если там нет места — в первом
свободном ряду, с сообщением, куда она встала.

### Этап 3 — провод по доске. Сделан.

Решение принято само: **вариант А**, провод несёт шину, зажим выводится. Обоснование: слой
взаимодействия при А и Б одинаков, различается только запись в проекте. Если понадобится Б, это
миграция модели, а взаимодействие переписывать не придётся. Обратное неверно: старт с Б стоил бы
дороже и выиграть можно было бы только угадав.

Новый метод стора `connectOnBoard(fromDeviceId, bus, toDeviceId)` пишет связь так же, как уже
существующий каскад: `circuitId` пустой, `kind: 'busbar'`, цвет из `wireColor`.

Критерий, проверенный в браузере:

1. `3` включает проведение, кнопка нажата.
2. В режиме проведения зажимы становятся мишенями — видно, что соединяемо.
3. Клик по зажиму A отмечает его началом, линия тянется за указателем.
4. Наведение на зажим B показывает маршрут до него.
5. Клик по B создаёт провод, и он приходит **в те же зажимы**, что и автоматический: лишних
   расстояний больше 2 px нет ни по одному проводу.
6. Соединение разных шин отклоняется с внятной причиной и ничего не создаёт.
7. Esc бросает недорисованный провод.
8. Отмена снимает только что проведённый провод.

## Находки, которые требуют решения отдельно

### Клеммные колодки — закрыто

`faceTerminalColumns` отдавал 0 для категории `terminals`, поэтому у колодки не было ни одного
зажима и провод в неё провести было нельзя. Причина была не в модели, а в том, что винты колодки
считались прямо в компоненте: рисунок знал, где его точки подключения, а домен — нет.

Геометрия винтов перенесена в `faceMetrics.faceSocketGrid`, компонент читает её оттуда же, и
`faceTerminals` строит из этих же винтов верхний и нижний зажим. Рисунок не изменился: это
проверяется отдельно — шесть винтов, два столбца, три ряда, тот же радиус.

Шину провода задаёт товар: колодка ЗБИ — PE, колодка ПВ — N, КВ — L. Провод в чужую шину
отклоняется тем же сообщением, что и в аппарат.

**Чем это ограничено.** У колодки шесть нарисованных винтов, а вариант А даёт ей два зажима — вход
и выход. Провод, приходящий на третий винт, по этой модели провести нельзя. Это не недоделка
инструмента, а следствие выбранной модели: шину несёт провод, а не зажим. Полноценные шесть
проводов — это вариант Б, миграция модели, которую по-прежнему никто не выбрал.

## Шапка доски: покрытие, которого не было

Визуальная базовая снимка снимает только рабочую область, поэтому шапка с панелью инструментов не
была покрыта ничем: кнопка под кнопкой или тема, возвращающаяся светлой после перезагрузки,
прошли бы весь набор.

Добавлено `tests/e2e/board-header.spec.ts`: тема переживает перезагрузку, ни одна кнопка не
перекрывает другую, все действия доступны по названию.

Первая версия проверки перекрытий проходила вхолостую: класс шапки в разметке `app-header`, а в
тесте стоял `board-header`, и ни один элемент не находился. Добавлен заслон — проверка обязана
видеть больше пяти элементов, иначе она ничего не проверяет.

Вложенность исключена намеренно: `label` по правилам оборачивает своё поле, и это не дефект.
Дефект — когда одно поле накрывает другое, и до накрытого нельзя добраться.
